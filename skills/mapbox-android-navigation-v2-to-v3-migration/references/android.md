# Android: Navigation SDK v2 → v3

Mappings from Navigation SDK for Android v2 to the current v3 APIs.

**Requirements for v3:** Kotlin 1.7.0+ (Java apps can call the public APIs), Android SDK 21+, Java 8 source and target compatibility. NDK 23 (default artifacts) or NDK 27, instead of NDK 21. NDK 27 artifacts (since 3.11.0) add the `-ndk27` suffix to the artifact ID, for example `com.mapbox.navigationcore:android-ndk27`, and support 16 KB page sizes. Keep the app's NDK choice: if the v2 app already used the v2 `-ndk27` artifacts, use the v3 `-ndk27` ones. Other NDK major versions aren't guaranteed to work. See the [requirements](https://docs.mapbox.com/android/navigation/guides/#requirements) for the targeted release. The v3 API surface still changes between minor releases, so target the latest stable 3.x and check its changelog.

**Maps SDK v11 is required.** Navigation SDK v3 depends on Maps SDK v11. Run `mapbox-android-maps-v10-to-v11-migration` for the map layer (map view, style, annotations, Maps camera, gestures, puck setup) before or alongside this migration. This file covers only the map pieces Navigation owns: route line, route arrow, navigation camera and the location provider Navigation feeds to the puck.

**Artifacts:** the Maven group changes from `com.mapbox.navigation` to `com.mapbox.navigationcore`. The all-in-one artifact `com.mapbox.navigation:android` becomes `com.mapbox.navigationcore:android`. Granular modules are listed under Dependencies and setup.

**Minimum versions for target APIs:** the high-level Coordination API (`NavigationPresenter`) and several route-line options need recent 3.x releases (route callouts through the presenter: 3.24+). Experimental APIs are marked ★. Check they exist in the version you target before using them.

## Behavior changes

Each row compiles in v3 (or is easy to make compile) but behaves differently at runtime. Present every row that applies as a decision.

| Change                          | v2                                                                                                                             | v3 default                                                                                                                                                  | To keep v2 behavior                                                                                                                                                  | Applies when                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Router                          | The app could plug in a custom `Router`; routes came from wherever it said                                                     | Built-in hybrid router: Directions API when online, onboard routing from cached tiles when offline. Custom routers can't be set.                            | Not possible. Decide how routes from a custom backend are brought in (see No direct mapping).                                                                        | The app set a custom router                                 |
| Alternatives                    | Alternatives requested or observed explicitly; switching to an online alternative was opt-in (`OnlineRouteAlternativesSwitch`) | Alternatives update automatically. With an offline primary route, the SDK **switches to an online alternative by itself**.                                  | `setContinuousAlternativesEnabled(false)` stops automatic updates, removal of passed alternatives and the automatic offline → online switch, all together.           | The app requested or observed alternatives, or runs offline |
| Routes set from outside the SDK | Any `DirectionsRoute` (from JSON or a custom backend) could become a `NavigationRoute`                                         | Routes come only from `requestRoutes` or `requestMapMatching` (★ `NavigationRouteObjectFactory` in recent 3.x may build one from an external route)         | Route the request through the SDK with silent waypoints (`waypointIndicesList`) or map matching, so the route the driver sees may differ slightly from the backend's | The app built `NavigationRoute`s from its own data          |
| Puck bearing                    | `mapView.location.puckBearingEnabled` defaulted to `true`                                                                      | Defaults to `false` (Maps v11)                                                                                                                              | Set `puckBearingEnabled = true` when setting up the puck                                                                                                             | The app shows the puck. Also listed in the Maps migration.  |
| Default location request        | Whatever `LocationEngineRequest` the app passed, or the v2 default                                                             | If `locationOptions` isn't set: 1000 ms interval, 500 ms minimum interval, `AccuracyLevel.HIGH`                                                             | Translate the app's v2 request into `LocationProviderRequest` and pass it through `LocationOptions.Builder().request(...)`                                           | The app set `locationEngineRequest`                         |
| Mock and replayed locations     | Replay used `ReplayLocationEngine`; no mock flag needed                                                                        | Custom providers declare `REAL`, `MOCKED` or `MIXED`. Mock locations must carry `LocationExtraKeys.IS_MOCK = true`.                                         | Pick the provider type that matches what the app feeds. Use `startReplayTripSession()` for replay.                                                                   | The app simulates, replays or injects locations             |
| Replay start order              | Events pushed to the app's `MapboxReplayer` before `startTripSession()` reached `ReplayLocationEngine`                         | The replay provider connects to `mapboxNavigation.mapboxReplayer` in `startReplayTripSession()`. Earlier events are lost: no location arrives               | Call `startReplayTripSession()` first, then `pushEvents(...)` / `playFirstLocation()`. | Posted speed limit              | `LocationMatcherResult.speedLimit.speedKmph`, always in km/h, plus the posted unit                                             | `speedLimitInfo.speed` is already in `speedLimitInfo.unit` (km/h or mph); `null` when unknown                                                               | Drop the app's km/h to mph conversion, or the value is converted twice                                                                                               | The app reads the speed limit itself                        |
| Route line vanishing offset     | `setVanishingOffset` before a route was set returned a value                                                                   | Returns an error if no route was set                                                                                                                        | Call it only after setting routes, or handle the error                                                                                                               | The app calls `setVanishingOffset` directly                 |
| Speed info                      | `updatePostedAndCurrentSpeed` always returned a value                                                                          | Returns `null` when current speed isn't available                                                                                                           | `value?.let { speedInfoView.render(it) }`. Decide what the UI shows meanwhile.                                                                                       | The app uses `MapboxSpeedInfoApi`                           |
| Map matching requests           | Made with Mapbox Java (`MapboxMapMatching`), billed as a separate API call                                                     | `mapboxNavigation.requestMapMatching`, billed as described on the Navigation SDK [pricing page](https://docs.mapbox.com/android/navigation/guides/pricing/) | No code change for billing. Point the developer to the pricing page; don't state costs (pricing advice is out of scope).                                             | The app used map matching                                   |
| Route refresh                   | Refresh worked if the route request allowed it                                                                                 | Same rule, but only the **active** route set is refreshed. Routes held for later or shown in preview aren't.                                                | Make sure `RouteOptions` has `enableRefresh(true)` and the refresh annotations. `applyDefaultNavigationOptions()` sets both.                                         | The app builds `RouteOptions` by hand                       |
| Drop-in UI                      | `NavigationView` provided the whole navigation screen                                                                          | Removed on Android                                                                                                                                          | Copy the v2 Drop-in sources into the app (on approval), UX Framework, or own UI (see Drop-in UI)                                                                     | The app uses `ui-dropin`                                    |
| UI widgets in core modules      | Maneuver, trip progress, speed limit, status and voice views shipped in their own modules                                      | Views moved to `ui-components` (status widgets too); data APIs moved to `tripdata` and `voice`. `MapboxSpeedLimitView` removed.                             | Re-add the views from `ui-components`. Replace `MapboxSpeedLimitView` with `MapboxSpeedInfoView` (it also shows the current speed).                                  | The app used any v2 UI widget                               |

## New in v3 and on by default

Keeping v2 behavior (SKILL.md rule 2) means turning these off during the migration and listing them in the report as available. Checked against v2.23 and v3.35 source.

| Feature                | v2                                 | v3 default                                                                                     | To keep v2 behavior                                                                                                                                                        | Applies when                                 |
| ---------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Automatic alternatives | See Behavior changes: Alternatives | The SDK updates alternatives, drops passed ones and switches offline → online routes by itself | `mapboxNavigation.setContinuousAlternativesEnabled(false)`. It turns off all three together; there's no finer switch                                                       | Always check                                 |
| Route line slot        | No slots (Maps v10)                | `MapboxRouteLineViewOptions` places the route line in the `middle` slot                        | Set `routeLineBelowLayerId(...)` or `slotName(...)` to the position v2 used. Whether the default moves the line depends on the style: compare before and after screenshots | The app shows a route line on a custom style |

`setContinuousAlternativesEnabled` is set per `MapboxNavigation` instance. With `MapboxNavigationApp`, the instance is destroyed when the last lifecycle owner stops and a new one is created on the next start, so call it in every `onAttached`.

Same default in v2 and v3, no action needed: hybrid router, route refresh and alternatives intervals (5 min), reroute options, sensors and debug logging (off), and the route line options (vanishing route line, independent inactive legs, restricted sections, soft traffic gradient, occlusion: all off). New in v3 and off by default: `TrafficOverrideOptions`, native route objects, route callouts and route line blur. Not checked: the default location provider compared with v2's `LocationEngine`.

## Drop-in UI

Drop-in UI (`com.mapbox.navigation:ui-dropin`, `NavigationView`) **isn't shipped in v3 on Android.** Its sources are public in the [v2 repository](https://github.com/mapbox/mapbox-navigation-android/tree/lts/v2) (`libnavui-dropin`, `libnavui-app`), and the v3 migration notes point there for apps that want to keep it. Present the options as a decision:

| Option                            | What it is                                                                                                                                                                                  | Fits when                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Copy the v2 Drop-in (recommended) | The v2 `NavigationView` sources become a module of the app, adapted to v3. The app keeps its screens, layouts and Drop-in customizations. See `android-drop-in-port.md`                     | The app wants the same screens with the least change. It can move to Compose later    |
| UX Framework                      | A separate, full navigation experience: `com.mapbox.navigationux:android`, initialized with `Dash.init(context, accessToken)`, shown with a `DashPresenter` and the `DashScreen` composable | The app wants a complete prebuilt navigation screen and can host Compose              |
| App's own UI on Navigation SDK    | `ui-components` views (maneuver, trip progress, speed info, buttons) + `ui-maps` route line, arrow and camera, or the Coordination API (`NavigationPresenter`)                              | The app wants control over layout and behavior and accepts rebuilding the screens now |

Notes for the decision:

- **Copying is recommended**: it is the closest to v2 behavior. It needs the developer's explicit yes to the license terms (SKILL.md rule 5); with no answer, don't copy and report Drop-in as an open decision. Say what the copied code costs: the app now owns about 8k lines of UI code, and the copy relies on v3 `internal` UI components that can change in any 3.x release (listed in `android-drop-in-port.md`).
- **Building the app's own UI in Compose.** Navigation SDK v3 has no Compose UI components: all `ui-components` views are Android Views, hosted in `AndroidView` from Compose. The copied Drop-in XML layouts can be the starting point, converted with Google's [migrate XML views to Jetpack Compose](https://developer.android.com/agents/skills/jetpack-compose/migration/migrate-xml-views-to-jetpack-compose/skill) skill. Keep that separate from the SDK migration.
- The UX Framework is a different product with its own configuration and customization APIs. It isn't a renamed `NavigationView`. Drop-in `ViewBinder` and style customizations don't carry over. Inventory every customization the app made so the developer can check each one against the target.
- The UX Framework docs describe it as beta, with snapshot dependencies and evaluation terms. Flag that to the developer. Don't decide for them.
- Mapbox support can help with Drop-in replacement. Say so in the report.

**Build toolchain.** A v2 app often builds with an Android Gradle Plugin (AGP) older than 8. Raise `compileSdk`, AGP and Gradle to what the target release needs: Gradle reports the minimum `compileSdk` from the libraries' metadata, and the Maps reference lists AndroidX minimums. Moving to AGP 8 (JDK 17) also brings, unrelated to the SDK API:

- `namespace` in each module's `build.gradle` replaces the manifest `package` attribute
- Java and Kotlin must target the same JVM version (set `kotlinOptions.jvmTarget` to match `compileOptions`)
- New `gradle.properties` defaults that change how `R` classes behave. Set `android.nonTransitiveRClass=false` and `android.nonFinalResIds=false` to keep the AGP 7 behavior, or fix the references
- R8 fails release builds on missing classes. Read `build/outputs/mapping/release/missing_rules.txt`, check each class is an optional dependency, and add the `-dontwarn` rules to a ProGuard file listed in `proguardFiles`. Seen with v3: `com.google.auto.value.AutoValue` (Mapbox Java models), `androidx.asynclayoutinflater.view.AsyncLayoutInflater` (Maps view annotations), `androidx.work.multiprocess.RemoteListenableWorker` (WorkManager)
- Libraries that were transitive through `ui-dropin` (for example Material Components) must be declared by the app
- Old build tools in the project may not run on JDK 17 (for example ktlint 0.41 needs `--add-opens java.base/java.util=ALL-UNNAMED`)

```kotlin
    .accessToken(token)
    .coordinates(points)
    .build()
mapMatching.enqueueCall(object : Callback<MapMatchingResponse> {
    override fun onResponse(call: Call<MapMatchingResponse>, response: Response<MapMatchingResponse>) {
        mapboxNavigation.setRoutes(response.body()?.matchings()?.map { it.toDirectionRoute() } ?: emptyList())
    }
    override fun onFailure(call: Call<MapMatchingResponse>, t: Throwable) {}
})

    }
    override fun failure(failure: MapMatchingFailure) {}
    override fun onCancel() {}
```

### 4. Trip session and location

| v2                                                                                         | v3 target                                                                                                                                                                     | Notes                                                                               |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `NavigationOptions.Builder(context).locationEngine(engine).locationEngineRequest(request)` | `.locationOptions(LocationOptions.Builder().request(LocationProviderRequest…).build())`                                                                                       | Leave `locationOptions` unset to use the default provider and request               |

| App-owned `MapboxReplayer()` + `ReplayProgressObserver`                                    | Same with `mapboxNavigation.mapboxReplayer` (create the observer in `onAttached`), or `ReplayRouteSession` ★                                                                  | `ReplayRouteSession` starts replay itself. | `resetTripSession()`                                                                       | `resetTripSession { }`                                                                                                                                                        | The callback is required                                                            |
| `android.location.Location` in observers and providers                                     | `com.mapbox.common.location.Location`                                                                                                                                         | Everywhere in the public API. | `Location("provider").apply { latitude = …; bearing = 10f }`                               | `Location.Builder().source("provider").latitude(…).bearing(10.0).build()`                                                                                                     | No public constructor. `bearing` and `speed` are nullable `Double`s                 |

```kotlin
    .accessToken(token)
    .locationEngine(ReplayLocationEngine(mapboxReplayer))

mapboxNavigation.startTripSession()

// v3
val options = NavigationOptions.Builder(context).build()
val mapboxNavigation = MapboxNavigationProvider.create(options)
mapboxNavigation.startReplayTripSession() // connects the replay location provider
val mapboxReplayer = mapboxNavigation.mapboxReplayer
mapboxReplayer.pushEvents(listOf(ReplayRouteMapper.mapToUpdateLocation(eventTimestamp, origin)))
mapboxReplayer.playFirstLocation() // lost if called before startReplayTripSession()
mapboxReplayer.play() // as in v2: pushed events run only while playing
```
